# Agent Harness MVP

TypeScript Harness для последовательной работы аналитика, frontend/backend
планировщиков, frontend/backend исполнителей, тестировщика и верификатора через LLM CLI.
Каждая роль запускается отдельным процессом с новым контекстом. Harness передаёт
исходную спецификацию, историю уточнений и содержимое артефактов предыдущих ролей.

## Быстрая проверка без рабочего окружения

Нужны **Node.js 22+** и Git. TypeScript компилируется в JavaScript при установке;
встроенное выполнение `.ts` и специальные флаги Node не используются.
Команды ниже рассчитаны на macOS/Linux. На Windows используйте WSL2 с Node и LLM CLI.

Для проверки из исходников:

```sh
npm ci
npm run typecheck
npm test
npm run demo
```

Демо использует детерминированный исполнитель вместо LLM и создаёт временный
учебный проект. Оно показывает уточнения, роли и два review, не меняет текущий
репозиторий, не вызывает LLM CLI и ничего не публикует.

## Установка команды один раз

Из готового установочного архива:

```sh
npm install -g ./agent-harness-mvp-0.1.0.tgz
agent-harness --help
```

Либо из распакованных исходников:

```sh
npm ci
npm link
```

После этого `agent-harness` доступен в любом репозитории. Не нужно копировать
Harness внутрь продуктового проекта или каждый раз указывать путь к нему.

## Запуск из текущего репозитория

Откройте терминал в нужном Git-репозитории или любой его подпапке:

```sh
agent-harness run ./task.json
```

Целевой корень определяется через Git из текущей директории. Для monorepo это
корень Git-репозитория, а не ближайший package.json. Установочная папка Harness
не становится рабочей папкой проекта. В конфигурации **нет projectRoot**.

`harness.config.json` в корне репозитория необязателен. Без него используются
LLM CLI из PATH, встроенные конвенции, HEAD как исходный ref, локальный коммит
без публикации и проверки typecheck/lint/test/build, найденные в package.json.
Если packageManager указывает pnpm/yarn, проверки используют его; иначе npm.
Если подходящих проверок нет, Harness требует их настроить и не выдаёт фиктивный успех.

Для настройки конкретного проекта:

```sh
agent-harness init
```

Команда создаёт в текущем репозитории `harness.config.json` и `harness.mcp.json`.
Существующие файлы не перезаписываются. Настройки не содержат путь к продуктовому
репозиторию или путь к встроенной базе знаний; её Harness находит внутри установки.
Определения MCP содержат локальные пути запуска и создаются заново на каждом ПК.
При необходимости дополните checks, setup, интеграции и другие настройки.

Можно явно выбрать общий файл настроек для нескольких репозиториев:

```sh
agent-harness run ./task.json --config /path/to/shared-settings.json
```

Он задаёт поведение, а рабочий репозиторий всё равно определяется текущей папкой.
Относительные пути настроек, например knowledgeRoot, считаются от файла конфигурации.
Относительный путь task.json считается от текущей директории терминала, а specPath
внутри задачи — от корня Git-репозитория. При переносе старого конфига удалите
projectRoot: устаревшее поле отклоняется с объяснением, чтобы не запустить работу не там.

## Подготовка рабочего окружения

Пошаговая инструкция переноса, все точки настройки, подключение рабочих MCP,
контракты API-скриптов и первый запуск: [Настройка на рабочем ПК](docs/work-pc-setup.md).

- Установите и авторизуйте LLM CLI по внутренней инструкции. Проверьте
  `llm-cli --help`: здесь CLI отсутствует, реальный запуск пока не проверен.
  Адаптер передаёт JSON-запрос через stdin, добавляет `--output-format json` и ожидает итоговое сообщение result
  с subtype=success. Отличия вашей версии меняются в src/agents/runner.ts.
  Совместимость со stdin/headless нужно проверить на рабочем CLI. Для коротких
  запросов доступен `runnerInput: "argv"` с ограничением 64000 байт; общий входной
  лимит задаёт maxInputBytes (по умолчанию 4000000).
- Подключите Codebase/UI MCP в LLM CLI. `harness.mcp.json` содержит определения
  заглушок, но не подключается к LLM CLI автоматически. Убедитесь, что серверы
  доступны из worktree и разрешены нужные операции без интерактивных подтверждений.
- Задача пока подаётся файлом по examples/task.json: description, areas, критерии
  приёмки и specPath. Получение исходной задачи по ключу трекера задач ещё не подключено.
  Аналитик создаст отдельный change OpenSpec; исходное ТЗ и основные specs не переписываются.

Для Git нужен существующий коммит в `baseRef`. Harness создаёт отдельную ветку
`codex/<task>-<uuid>` и worktree от **локального** ref. Незакоммиченные изменения
основного checkout туда не копируются. Fetch автоматически не выполняется:
перед запуском обновите нужный ref самостоятельно. Если нужны зависимости в новом
worktree, добавьте явный `setup`, например:

```json
"setup": [{ "command": "npm", "args": ["ci"] }]
```

Команды `setup` исполняются один раз перед агентами. Затем работают роли и проверки.
После успешных проверок Harness создаёт локальный коммит продуктовых изменений
вместе с документами change OpenSpec;
`.harness` в него не попадает. Worktree сохраняется для просмотра. Для проверки
без Git можно задать `git.enabled=false`: тогда агенты работают прямо в projectRoot.

## Артефакты OpenSpec

Каждый запуск создаёт собственный `openspec/changes/task-<run-id>/`:

```text
.openspec.yaml                 # schema: spec-driven, создаёт Harness
proposal.md                    # аналитик: цель и границы изменения
specs/<capability>/spec.md      # аналитик: изменения требований и сценарии
design.md                      # backend/frontend-планировщики: общее решение
tasks.md                       # общий checklist реализации и проверок
```

Backend-планировщик задаёт API-контракт, frontend-планировщик дополняет дизайн и
задачи. Исполнители отмечают только задачи своей области; тестировщик — testing.
Документы пишутся черновиками в артефакты роли и публикуются кодом после проверки.
Без полного одобренного плана реализация не стартует. COMPLETED требует выполненных
задач, подтверждения тестировщика, успешных проверок и одобрения верификатора.
Документы change сохраняются в Git вместе с кодом; archive/merge не выполняются.

Встроенные проверки контролируют контракт Harness. Для полной проверки формата
установите OpenSpec CLI на рабочем ПК и добавьте в конфигурацию:

```json
"openspec": { "validator": { "command": "openspec", "args": [] } }
```

Тогда Harness вызовет `openspec validate <change> --type change --strict --no-interactive`
перед реализацией и перед доставкой. Без этой настройки CLI не требуется.
Настройка обязательна, если прохождение официального валидатора — условие вашего процесса.
Ответственность ролей, формат задач и ограничения: [docs/openspec.md](docs/openspec.md).

## Уточнения и результаты

```text
Аналитик → backend/frontend-план → проверки плана → верификатор плана
                   ↑                                      │
                   └──────── доработка плана ──────────────┘
                                                          ↓ одобрено
            backend/frontend-код → тестировщик → проверки → верификатор реализации
                   ↑                                      │
                   └────── доработка реализации ───────────┘
                                                          ↓ одобрено
                               Harness: коммит → [push и PR, если включены]
```

При задаче только одного направления ненужные планировщик и исполнитель пропускаются.
Верификатор реализации может вернуть задачу и к планированию. После изменения плана
реализация и тестирование выполняются повторно.

По умолчанию `maxReworkRetries=2`: первоначальная попытка + две доработки отдельно
для плана и реализации. Счётчики сохраняются при уточнениях и не сбрасываются при
`resume`. После третьего отрицательного review — BLOCKED, `nextRole=developer`,
артефакт `escalation.md`; коммит/PR не создаются. Подробный контракт:
[docs/verification.md](docs/verification.md).

- `WAITING_REVIEW`: проверки пройдены, изменения опубликованы в PR; ожидание ревью/merge.
- `COMPLETED`: PR смержен; в режиме без публикации — проверенная локальная реализация.
- `CANCELLED`: PR закрыт без merge; автоматизация остановлена.
- `NEEDS_CLARIFICATION`: есть конкретные вопросы, их контекст и блокируемая работа.
  Последующие роли не запускаются; следующий участник — аналитик.
- `BLOCKED`: ошибка процесса, недоступная зависимость, дефект, непрошедшая проверка
  или ошибка публикации. Причина сохраняется в отчёте.

```sh
agent-harness status <run-id>
agent-harness resume <run-id> ./answers.md
agent-harness resume <run-id> --answer "Сохранять ввод и показывать ошибку"
```

Ответы передаются новым проходом вместе с исходной спецификацией. Аналитик создаёт
обновлённые proposal и delta specs; планировщики заново формируют design/tasks.
Предыдущие артефакты и вопросы сохраняются. `maxIterations` ограничивает цикл.
Если код уже изменён до вопроса, он сохраняется в том же worktree.

После временной ошибки коммита, push или создания PR, возникшей уже после одобрения:

```sh
agent-harness retry-delivery <run-id>
```

Команда повторяет проверки и доставку без нового вызова LLM. Она требует действующих
одобрений и неизменности проверенных файлов. Эскалацию или отсутствие одобрения
этой командой обойти нельзя. Изменение кода после review требует новой верификации.

В `.harness/runs/<run-id>/` лежат `state.json`, `report.md`, снимок исходной
спецификации, запросы, ответы и логи ролей/проверок. Артефакты ролей лежат в
worktree `.harness/artifacts/<run-id>/<iteration>/<role>/`. Снимки документов change
после каждого завершённого этапа — в `<iteration>-<role>.openspec/` внутри run.
При повторном вызове добавляется `-attempt-N`; review имеют имена `verifier-plan`
и `verifier-implementation`. Ни один отчёт предыдущей попытки не перезаписывается.
Не запускайте один run одновременно. После аварийного завершения сначала убедитесь,
что процессы остановлены. Для новых запусков `continue` умеет восстановить
блокировку отсутствующего процесса на том же ПК.

Чтобы найти задачу и продолжить после остановки:

```sh
agent-harness list
agent-harness continue <run-id>
```

Завершённые роли не повторяются; незавершённый этап запускается заново в том же
worktree с сохранённым контекстом. Уточнения требуют `resume` с ответом,
эскалацию разработчику `continue` не обходит. Для старых запусков без checkpoint
автоматическое восстановление недоступно. Условия и ограничения:
[docs/continuation.md](docs/continuation.md).

Коды CLI: `0` — COMPLETED/WAITING_REVIEW, `4` — CANCELLED, `2` — NEEDS_CLARIFICATION, `3` — BLOCKED,
`1` — ошибка команды/конфигурации. `status` только читает сохранённое состояние.

## MCP-заглушки

Локальные stdio MCP-серверы на [официальном TypeScript SDK v1](https://ts.sdk.modelcontextprotocol.io/server):

```sh
node dist/scripts/mcp-stub.js codebase
node dist/scripts/mcp-stub.js ui
```

Они ожидают MCP-клиент на stdin; вручную вводить обычный текст не нужно.

- Codebase: `search_knowledge`, `find_usage_example`.
- UI: `get_kb`, `get_rule`, `get_ui_quality_checklist`.

Каждый ответ содержит `mock=true`. Это минимальные учебные контракты, а не копия
полного API рабочих MCP. Заглушки не выполняют визуальную проверку интерфейса.
Реальные имена инструментов и параметры можно добавить в этом файле после переноса.
Агенту запрещено выдавать ответ заглушки за сведения о корпоративных библиотеках.

## Git, Bitbucket и трекер задач

Git вызывается кодом через CLI с массивом аргументов, без shell. Bitbucket и
трекер задач — внешние скрипты, также без MCP. В конфигурации задаются `command` и `args`:

```json
"integrations": {
  "taskTracker": { "command": "node", "args": ["/absolute/path/task-tracker-adapter.js"] },
  "bitbucket": { "command": "node", "args": ["/absolute/path/bitbucket-adapter.js"] }
}
```

Скрипт получает один JSON-запрос на stdin и возвращает один JSON-ответ на stdout.
Логи пишет в stderr, при ошибке возвращает ненулевой exit code. Передавайте секреты
через окружение, не через task/config. Подробный контракт: [docs/integrations.md](docs/integrations.md).
`scripts/mock-integration.ts` — пример без сетевых вызовов.

При `git.publish=true` Harness выполняет push в `origin` и вызывает создание PR.
Нужно настроить настоящий Bitbucket-адаптер; в комплекте он заменён заглушкой.
Merge выполняет разработчик. При `publish=false` публикации нет.

Аналитик сначала ищет ответы в ТЗ, OpenSpec, коде, тестах и документации,
в том числе через Codebase MCP. Если блокирующий вопрос остаётся, сохраняет
clarification-N.md и возвращает NEEDS_CLARIFICATION. Harness передаёт вопросы
в `task.report`: рабочий скрипт публикует комментарий в трекере задач. Следующие
этапы ждут ответа, который пока передаётся через `resume` (автоматическое чтение
комментариев не подключено). Вопросы также доступны в CLI и локальном артефакте.
Если адаптер упал, это видно в integrationErrors; статус запуска сохраняется отдельно.

Рабочий скрипт публикует вопросы и итоговые комментарии через API под своей авторизованной
учётной записью. Личный токен означает действия от владельца токена; для отдельного
автора нужна сервисная учётка с соответствующими правами. LLM собственных credentials
не получает и комментарии напрямую не отправляет. Заглушка сетевых запросов не делает.
Эскалация разработчику передаётся тем же `task.report` с `returnToRole=developer`,
счётчиками повторов и отчётом. Без рабочего адаптера она существует как локальный артефакт.

## Границы первой версии

- Процессы LLM CLI не изолированы контейнером. Ограничения ролей на запись и Git
  описаны в инструкциях, но не являются OS sandbox. Рабочие ограничения инструментов
  необходимо настроить в LLM CLI. Не запускайте непроверенные задачи с production-доступами.
- Harness не обеспечивает получение задачи/ответов по webhook: вход и ответы — файлы.
- Тестировщик добавляет тесты и фиксирует дефекты. Верификатор направляет доработки;
  код исправляют исполнители. Параллельной работы ролей и merge нет.
- Knowledge маршрутизируется по роли: небольшой домен загружается в контекст.
  Skill `skills/project-conventions/SKILL.md` включается явно, установка в Codex не нужна.
  Для большой базы следующим шагом станет выбор отдельных файлов по индексу.
- MCP, Bitbucket, трекер задач и реальная версия LLM CLI требуют проверки на рабочем ПК.

## Наблюдение за ревью PR

После публикации запускайте `agent-harness watch <run-id> --loop`: первая проверка
сразу, следующие через час. Для внешнего расписания используйте `watch <run-id>`
без `--loop`. Сам `run` создаёт PR и возвращает WAITING_REVIEW; наблюдение запускается
отдельно либо флагом `agent-harness run task.json --watch`. После merge статус COMPLETED, после закрытия без merge — CANCELLED.

Review-triager разбирает новые/изменённые треды: направляет подтверждённые замечания
исполнителям или планировщикам, формирует доказательный ответ либо вопрос ревьюеру.
Исправления проходят тестировщика, обязательные проверки и верификатора, затем
push в прежнюю ветку и ответ в треде. Две коррекции на тред, затем эскалация.
Треды автоматически не закрываются. Корпоративные API пока заменены заглушкой.

Быстрая локальная демонстрация: `agent-harness demo-review`.
Полный путь и ограничения: [docs/pr-review.md](docs/pr-review.md).

## Навигация по исходникам

Карта модулей, зависимости и точки входа: [docs/architecture.md](docs/architecture.md).
CLI находится в `src/cli`, выполнение задачи — в `src/workflow`, цикл PR — в
`src/review`. Общение с LLM CLI, правила OpenSpec и внешние интеграции вынесены
в собственные папки. `agents/` содержит инструкции LLM по папкам `analysis`, `backend`, `frontend`,
`testing`, `review`, а `src/agents/` — код их запуска. Общий контракт — `agents/common.md`.

Перед изменениями используйте `npm run typecheck`, `npm test` и
`npm run format:check`. `npm run format` применяет единое форматирование.
Сборка очищает `dist`, поэтому удалённые модули не попадают в переносимый пакет.

## История выполнения

`agent-harness events <run-id>` выводит историю этапов из `events.jsonl`: запуски
ролей, ошибки, проверки, решения верификатора, публикацию и ответы на ревью.
История сохраняется при resume и следующих проходах watch. `state.json` остаётся
контрольной точкой продолжения; журнал служит для диагностики, автоматического
проигрывания событий нет. Подробности: [docs/events.md](docs/events.md).

Использованные идеи из открытых проектов и ссылки на исходники:
[docs/upstream-patterns.md](docs/upstream-patterns.md).

## Контракт артефактов

Каждая роль возвращает общий JSON AgentResult и обязательный Markdown-отчёт
по фактическому статусу. Каталог ролей и имён отчётов — `src/agents/contracts.ts`,
шаблоны — `agents/templates/`. Заголовки шаблона задают обязательные разделы
и автоматически добавляются в инструкции роли. Код отклоняет отсутствующий отчёт,
неполные/пустые разделы и отсутствие обязательного структурированного решения.
Проверка выполняется до публикации OpenSpec и передачи результата следующей роли.
Матрица файлов и ограничения проверки: [docs/artifacts.md](docs/artifacts.md).

Исправления по независимому ревью и покрывающие их сценарии:
[docs/review-fixes.md](docs/review-fixes.md).

Тестировщик также описывает воспроизводимые тест-кейсы в test-report.md.
Подготовка тестовых данных и создание тест-стори после аппрува PR запланированы
в [docs/todo.md](docs/todo.md).
