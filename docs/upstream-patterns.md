# Что заимствуем из других harness-проектов

Проверено 30 октября 2026 года по исходному коду upstream. Ссылки на `main`
изменяемые; исследование не фиксирует SHA и не является проверкой конкретного
релиза. Проекты не запускались. Ниже отдельно обозначены наблюдения и наши
адаптации; чужой исходный код не переносился.

## Компактный цикл: mini-swe-agent

**Проверено.** `DefaultAgent` разделяет `run`, `step`, `query` и
`execute_actions`. Общий цикл сохраняет траекторию в `finally`, в том числе при
ошибке; лимиты проверяются перед запросом модели.
[Источник: default.py](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/agents/default.py).

**Адаптация для нас.** Единая функция запуска роли должна сохранять запрос,
stdout/stderr и результат, проверять артефакты и обеспечивать одинаковые
события начала/окончания. Порядок этапов и решения о повторе остаются в workflow. Правила публикации
черновиков по-прежнему принадлежат модулю openspec. Наш шаг — целый запуск LLM CLI, тогда как upstream `step`
выполняет один обмен с моделью и действия окружения. Второй внутренний цикл
инструментов поверх LLM CLI нам не нужен.

## Наблюдаемость: OpenHands SDK

**Проверено.** Базовое событие неизменяемое, имеет идентификатор, время,
источник и связь с родителем.
[Источник: event/base.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/event/base.py).
`EventLog` хранит события отдельными файлами, индексирует ID, блокирует запись и
отклоняет повторный ID. Последовательность записи служит устойчивым курсором.
[Источник: conversation/event_store.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/event_store.py).

**Адаптация для нас.** Небольшой дописываемый `events.jsonl` для истории
этапов, запусков ролей, проверок и ответов на ревью. `state.json` остаётся
контрольной точкой продолжения; восстанавливать состояние проигрыванием журнала
мы не обещаем. Это упрощённый аудит, а не реализация хранилища OpenHands.
Для порядка использовать последовательность записей, а не только часы.

## Повторные ответы и область ревью: PR-Agent

**Проверено.** В Cloud-провайдере разделены получение текущего HEAD и
публикация комментариев. `publish_inline_comments` специально учитывает
частичную публикацию: повтор всей пачки способен создать дубли.
[Источник: bitbucket_provider.py](https://github.com/The-PR-Agent/pr-agent/blob/main/pr_agent/git_providers/bitbucket_provider.py).
Для Bitbucket Server существует отдельный провайдер с собственными URL и
авторизацией; Cloud-контракт нельзя считать готовой интеграцией с Server.
[Источник: bitbucket_server_provider.py](https://github.com/The-PR-Agent/pr-agent/blob/main/pr_agent/git_providers/bitbucket_server_provider.py).

`PRReviewer` поддерживает инкрементальный режим и пропускает ревью, если нет
новых файлов.
[Источник: pr_reviewer.py](https://github.com/The-PR-Agent/pr-agent/blob/main/pr_agent/tools/pr_reviewer.py).
Согласование замечаний разрешает признать исчезнувшую проблему исправленной
только после полного успешного ревью при известных различных HEAD. Частичная
проверка не доказывает отсутствие старой проблемы.
[Источник: review_finding_state.py](https://github.com/The-PR-Agent/pr-agent/blob/main/pr_agent/algo/review_finding_state.py).

**Адаптация для нас.** Сохранять ответ до API-вызова и повторять его с тем же
ключом идемпотентности. Перед повтором сверять PR, HEAD и версию обсуждения;
устаревший ответ отправлять на повторный разбор. Проверка одного треда должна
передавать соответствующую область контекста, а не выдавать себя за полное
ревью реализации. Дедупликацию при потере ответа HTTP обязан поддержать реальный
адаптер: локального ключа самого по себе недостаточно.

## Роли и передача контекста: BMAD

**Проверено.** В текущей структуре роли описаны отдельными skills:
[аналитик](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-agent-analyst/SKILL.md),
[архитектор](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-agent-architect/SKILL.md),
[разработчик](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-agent-dev/SKILL.md).
Они сначала читают рабочую задачу, затем связанные материалы по необходимости.
Поведением управляют инструкции роли и настройки проекта.

**Вывод для нас.** Сохраняем отдельные роли и явные артефакты передачи.
Интерактивные меню, персоны и установщик BMAD не требуются для автоматического
конвейера. OpenSpec уже задаёт наши документы, заменять его форматом BMAD
оснований нет. Старые ссылки на `src/bmm/agents/*.yaml` не соответствуют
просмотренной ветке.

## Что проверить при адаптации

- После ошибки роли остаются логи и событие ошибки; общая функция сохраняет
  прежние пути артефактов и контроль неизменности файлов у верификатора.
- Возобновление дописывает историю, не стирает её; отсутствие журнала у старого
  запуска допустимо. Повреждённый хвост журнала не превращается в новое состояние.
- После успешного API-вызова с потерянным ответом повтор не дублирует комментарий.
- Отредактированный, удалённый или закрытый тред не получает старый ответ.
  Новый HEAD также останавливает публикацию по старому контексту.
- Проверка одного треда не закрывает другие замечания и не сбрасывает их лимиты
  повторов. Полное ревью по-прежнему получает полный план и результаты проверок.

Реальные LLM CLI, Bitbucket и трекер задач этим исследованием не проверялись.
Внешние адаптеры проекта пока остаются заглушками.
