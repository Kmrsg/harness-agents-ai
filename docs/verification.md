# Верификация и доработки

Одна роль `verifier` запускается отдельным процессом в двух режимах:

1. `plan`: проверяет соответствие design/tasks исходному ТЗ, proposal и delta specs.
2. `implementation`: проверяет фактическую реализацию по одобренному плану и specs,
   с учётом отчёта тестировщика и результатов обязательных проверок.

Верификатор не меняет код и документы. Изменение продуктовых файлов во время review
обнаруживается по fingerprint и блокирует продолжение. Это проверка после запуска,
а не изоляция процесса; ограничения инструментов нужно также настроить в LLM CLI.

## Контракт решения

Вход `AgentRequest.verification` содержит `phase` и номер текущего review `attempt`.
`rework` содержит тип доработки, номер использованной попытки и findings предыдущего
review. `checks` содержит результаты и последние 64 КБ вывода каждой текущей проверки.
История запросов/ответов сохраняется полностью; в активном контексте — последние
артефакты каждой роли/типа review, чтобы не накапливать устаревшие полные документы.

Ответ использует обычный AgentResult и дополнительное поле:

```json
{
  "status": "COMPLETED",
  "summary": "План не учитывает ошибку сохранения",
  "artifacts": [".harness/artifacts/.../verification-report.md"],
  "questions": [],
  "acceptance": [],
  "verification": {
    "phase": "plan",
    "verdict": "REWORK_PLAN",
    "findings": [{
      "id": "V1",
      "description": "Добавить обработку ошибки сохранения в дизайн и задачи",
      "evidence": "specs/requests/spec.md: AC-2; в design/tasks сценарий отсутствует",
      "criteria": ["AC-2"],
      "tasks": ["2.1"]
    }]
  }
}
```

`COMPLETED` здесь означает завершённый review, а не выполнение всей задачи.

| Verdict | Действие Harness |
|---|---|
| APPROVED | Продолжает процесс; обязательны доказательства по всем AC-id и пустой findings |
| REWORK_PLAN | Возвращает участвующим backend/frontend-планировщикам, затем повторно проверяет план |
| REWORK_IMPLEMENTATION | Повторяет участвующих исполнителей, тестировщика, проверки и review реализации |

На этапе plan допустимы APPROVED и REWORK_PLAN. Верификатор реализации может вернуть
работу в любой из двух этапов. Замечания обязаны содержать описание, доказательство
и ссылку хотя бы на один существующий критерий или task-id. Один только COMPLETED
без структурированного решения продолжить процесс не позволяет.

При NEEDS_CLARIFICATION вопросы сохраняются локально и передаются настроенному
скрипту трекера задач для публикации комментария. Ответ передаётся аналитику через resume. При BLOCKED
самого верификатора формируется эскалация разработчику: продолжать без review нельзя.
Невалидный JSON, нарушение владения артефактами и сбой запуска процесса дают BLOCKED;
это технические ошибки, а не разрешение на бесконечные вызовы агента.

## Две доработки

`maxReworkRetries` по умолчанию равен 2 и отдельно применяется к plan/implementation.
Таким образом, на каждую ветку доступны первоначальная попытка и две доработки.
Третий отрицательный review исчерпывает бюджет. Верификатор не управляет счётчиком.
Значение явно настраивается в конфигурации, от 0 до 10; пример использует 2.

Перед доработкой Harness сбрасывает флажки задач и аннулирует одобрение реализации.
При доработке плана аннулируется также одобрение плана. После его пересмотра
исполнители и тестировщик запускаются снова. В MVP повторяются все участвующие
роли выбранного этапа: это позволяет перепроверить общий frontend/backend-контракт.
Автоматического точечного выбора одной области по тексту замечаний нет.

Счётчики хранятся в `state.verification.retries` и сохраняются при `resume` после
уточнений. Отчёты и черновики не перезаписываются: повторные вызовы имеют суффикс
`-attempt-N`; review разделены на `verifier-plan` и `verifier-implementation`.

После исчерпания бюджета:

- `status=BLOCKED`, `nextRole=developer`;
- `escalation.md` содержит решения, замечания, доказательства и ссылки на проверки;
- `task.report` передаёт эскалацию настроенному скрипту трекера задач;
- коммит, push и PR не выполняются.

Без рабочего адаптера трекера задач эскалация остаётся локальным артефактом.

## Условия публикации

Верификатор принимает решение, а Git и Bitbucket вызывает Harness. Для доставки
нужны действующее одобрение плана, одобрение реализации, завершённый тестировщик
с подтверждением всех критериев и успешные обязательные проверки. Прошлые неуспешные
проверки остаются в истории; решение учитывает результаты текущей попытки.
Одобрение при упавшей текущей проверке отклоняется кодом и эскалируется разработчику.

Одобрение привязано к содержимому документов плана и продуктовых файлов. Флажки
задач могут меняться в ходе реализации без изменения смысла плана. Прочие изменения
плана требуют повторного review. Изменение продуктовых файлов после финального
одобрения делает его непригодным для публикации.

`retry-delivery` доступен только при ошибке коммита/push/PR, возникшей уже после
одобрения. Он повторяет проверки и доставку, но не вызывает LLM и не сбрасывает
бюджеты. Эскалацию или отсутствие review таким способом обойти нельзя.
`git.publish=false` сохраняет прежний режим локального коммита; merge не выполняется.
