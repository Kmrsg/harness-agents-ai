# Контракт артефактов

Структура результата проверяется одинаково для обычного workflow и PR-triager.
Каждый запуск роли возвращает JSON AgentResult и файлы, перечисленные в artifacts.
Обязательный отчёт создаётся непосредственно в переданном artifactDirectory;
пути в JSON считаются относительно workdir. Отчёт из другой или вложенной папки
не заменяет обязательный файл. Пути, симлинки и размеры дополнительно проверяются
в src/agents/artifacts.ts.

## Каталог и шаблоны

`src/agents/contracts.ts` задаёт группу роли, имя отчёта COMPLETED и режим чтения
для верификатора/triager. Обязательные разделы ## берутся из соответствующего
Markdown-шаблона в `agents/templates/`. Тот же полный шаблон автоматически включается
в instructions роли. Изменение заголовка шаблона одновременно меняет инструкции
и проверку, отдельного дублирующего списка секций нет.

| Роль при COMPLETED | Обязательный отчёт | Другой обязательный результат |
| --- | --- | --- |
| analyst | analysis-report.md | proposal.md и specs/<capability>/spec.md в openspec.draftDirectory |
| backend/frontend planner | planning-report.md | Полные общие design.md и tasks.md в openspec.draftDirectory |
| backend/frontend implementer | implementation.md | Код и полная копия tasks.md с флажками своей области |
| tester | test-report.md | Тест-кейсы в Test Cases, оценки acceptance по AC-id и копия tasks.md с флажками testing |
| verifier | verification-report.md | Структурированное JSON verification с фазой и вердиктом |
| review-triager | review-report.md | Структурированное JSON reviewDecision |

Backend и frontend используют одинаковые имена отчётов, но отчёты находятся
в разных artifactDirectory. Для frontend-implementer используется отдельный шаблон
`agents/templates/frontend-implementation.md`, сохраняющий имя `implementation.md`.
Он дополнительно требует непустой раздел `UI Rules`: источники правил и примеров,
полученные требования, места применения и противоречия с утверждённым планом.
Если раздел неприменим, исполнитель объясняет причину. Нужные реальные правила
не заменяются MCP-заглушками. Верификатор оценивает соответствие правилам по
отчёту и коду; наличие раздела само по себе не доказывает вызов MCP.
Существенное противоречие, найденное исполнителем, возвращается как BLOCKED
с необходимостью перепланирования в Recovery; автоматического маршрута из этого
статуса к планировщику нет. Верификатор может использовать существующий REWORK_PLAN.
Верификатор плана и реализации также имеет отдельные
каталоги запусков. Поэтому одинаковые имена файлов не перезаписывают чужой результат.

## Тест-кейсы

Тестировщик описывает каждый тест-кейс с TC-id, связью с AC/specs, предусловиями,
данными, шагами, ожидаемым и фактическим результатом и статусом PASS/FAIL/NOT_RUN.
Раздел Test Cases обязателен для завершённого отчёта; код проверяет его наличие
и заполненность, а полноту сценариев оценивает верификатор. Подготовка данных,
скрипты и создание тест-стори после аппрува PR пока запланированы в
[todo.md](todo.md), автоматизации этих действий нет.

## Уточнение и блокировка

Для любой роли при NEEDS_CLARIFICATION нужен clarification.md с разделами Summary,
Questions, Investigated, Blocked Work. Вопросы возвращаются также в JSON questions;
id уникальны и каждый должен присутствовать в разделе Questions отчёта.
При BLOCKED нужен blocked.md с Summary, Cause, Evidence, Recovery.
Отчёт успеха и завершённые OpenSpec-документы в этих статусах не требуются.
Черновики в этих статусах не публикуются. Triager при блокировке останавливает
цикл PR с ясной причиной; обычные уточнения ревьюера возвращаются через
COMPLETED + reviewDecision.action=CLARIFY.

## Что проверяет код

До публикации OpenSpec и передачи контекста следующей роли:

- Базовую структуру JSON, допустимые статусы, вопросы и acceptance.
- Наличие отчёта с точным именем и всех обязательных разделов шаблона.
- Непустое содержимое каждого раздела: комментарии, заголовки и {{placeholder}}
  содержимым не считаются; один TODO/TBD также не принимается.
- Повторяющиеся заголовки и попытку заменить раздел заголовком внутри fenced code.
- Наличие verification/reviewDecision у соответствующей завершённой роли;
  другую роль с этими полями отклоняет.
- Правила OpenSpec: обязательные документы, разделы design, specs, владельцев
  и флажки tasks. Отчёт не заменяет эти проверки.

Дополнительные доказательства допускаются внутри artifactDirectory. Они не
заменяют обязательный отчёт. Для неприменимого раздела указывайте причину;
не оставляйте его пустым и не выдумывайте проверку.

У принятого результата сохраняются artifactDirectory и artifactManifest с SHA-256
содержимого каждого файла. Перед восстановлением контекста для continue/PR-исправления
проверяются digest, размер, регулярный тип файла и пути. Симлинки, включая замену
назначенного каталога, не разрешены. Отсутствующий manifest у старого результата
не подменяется новым digest: автоматическое повторное использование останавливается.

## Ошибки и границы проверки

Невалидный контракт — технический BLOCKED с указанием файла/раздела. Частичный
результат не добавляется в state.results и не передаётся следующей роли. Запрос,
сырой ответ и логи сохраняются, если процесс успел их вернуть; ошибка попадает
в журнал событий. Контрактные ошибки не запускают бесконечные повторы.

Проверяется структура, а не достоверность произвольного текста. Соответствие
выводов коду и требованиям оценивается тестировщиком и верификатором; зелёные
проверки и evidence остаются обязательными. Markdown не сравнивается семантически
с JSON: роли должны поддерживать их согласованность, проверяющий читает оба.

Старые результаты на диске не переписываются и не мигрируются. Каждый новый
вызов роли получает текущий контракт и проверяется по нему. Формат основных
полей AgentResult и имена существующих файлов запросов/логов сохранены.
