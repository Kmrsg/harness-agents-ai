# Прерывание и продолжение задачи

## Пользовательский путь

Из продуктового репозитория выполните:

```sh
agent-harness list
agent-harness status <run-id>
agent-harness continue <run-id>
```

`list` выводит JSON-массив запусков этого репозитория, от новых к старым:
run-id, ключ и название задачи, статус, этап, следующая роль, время изменения,
PR и каталог запуска. Повреждённый state.json показывается как отдельная ошибка;
остальные задачи остаются видимыми. Пустая история даёт `[]`.

`continue` принимает run-id либо путь к каталогу запуска. Команда выполняет
оставшуюся работу и возвращает обычный результат CLI. Это не команда создания
нового run. Сохраняются ветка, worktree, исходное ТЗ, конфиг-снимок, итерация,
завершённые результаты и счётчики доработок.

## Что повторяется после остановки

| Момент остановки | Продолжение |
| --- | --- |
| Setup | Завершённые setup-команды пропускаются, незавершённая повторяется |
| Аналитик, планировщик, исполнитель, тестировщик | Завершённые роли пропускаются, незавершённая вызывается заново |
| Проверки | Повторяется блок проверок текущей фазы; роли перед ним не запускаются заново |
| Верификатор | Повторяется незавершённое review с восстановленными результатами проверок |
| Доставка после одобрения | Используется механизм retry-delivery с перепроверкой файлов и команд |
| Ожидание PR | Выполняется один проход наблюдения; для постоянного цикла используйте watch --loop |
| Исправление PR | Восстанавливается фаза исправления, если исходная ветка и обсуждение по-прежнему актуальны |

Новый процесс LLM CLI получает исходное ТЗ, OpenSpec, историю уточнений,
отчёты завершённых ролей, результаты проверок и замечания rework/PR. Скрытое
состояние старой LLM-сессии не восстанавливается. Частичные изменения кода
остаются в worktree: новая попытка видит их и должна завершить работу с ними.

Результат считается завершённым, когда он прошёл проверку контракта и был
зафиксирован в state.json. Если роль успела отработать, но процесс погиб раньше
сохранения этой точки, вызов может повториться. Поэтому выполняемые агентами
действия и setup должны допускать повтор. Гарантии «ровно один запуск» нет.
Неполностью опубликованные OpenSpec-документы могут потребовать ручной проверки,
если восстановление обнаружит изменение уже одобренного плана.

Запросы и артефакты повторной попытки получают суффикс `-attempt-N`, прежние
доступные файлы сохраняются. Номер вызова роли увеличивается, бюджет доработок
верификатора от простого continue не расходуется и не сбрасывается. Если новое
review запросит доработку, действуют прежние лимиты.

## Ctrl+C и аварийное завершение

При Ctrl+C/SIGTERM во время дочерней команды Harness останавливает её группу
процессов, сохраняет BLOCKED с `interrupted=true` и освобождает блокировку.
Прерванная проверка не превращается в обычный дефект с последующим review.
Если сигнал пришёл между командами, процесс может завершиться раньше обработки:
восстановление использует последнюю сохранённую точку RUNNING.

После kill -9 или аварии питания на диске может остаться RUNNING и run.lock.
Новые блокировки содержат PID и hostname. Команда continue автоматически снимает
блокировку только заведомо отсутствующего процесса на том же ПК. Работающий PID,
неизвестный владелец или другой hostname требуют проверки человеком; возраст
файла не является основанием снимать блокировку.

Дочерние процессы также учитываются в `<run>/processes/`. После аварии родителя
LLM CLI или проверка могут ещё работать. В таком случае continue сообщит PID
группы и откажется начинать новую запись. Остановите прежний процесс и повторите
команду. Harness не завершает неизвестные живые процессы автоматически.
Учёт процессов не является OS sandbox или переносимой системой управления
службами; не запускайте команды, которые бесконтрольно оставляют фоновые сервисы.

Если осталась старая пустая run.lock или run.lock.recovery после аварии самого
восстановления, сначала убедитесь, что владельцы и дочерние процессы остановлены,
и лишь затем удалите соответствующий файл вручную. Автоматически угадывать
владельца такой блокировки Harness не будет.

## Проверки перед продолжением

- Workdir существует и остаётся той же веткой и worktree того же Git-репозитория.
- HEAD не менялся извне. Коммит доставки, созданный непосредственно перед
  прерыванием, распознаётся по родителю, сообщению и одобренному содержимому.
- Сохранённый одобренный план не изменился (переключение флажков tasks разрешено).
- На границе завершённого этапа файлы совпадают с сохранённым fingerprint.
  Для незавершённого пишущего агента допускаются его частичные изменения.
- Незавершённый read-only reviewer не изменил продуктовые файлы.
- Отчёты и черновики завершённых ролей проходят проверку digest, размера и путей;
  замена содержимого, симлинк или выход из назначенного каталога не принимаются.
- При исправлении PR сохранённый тред не изменился, не удалён и не закрыт;
  исходный SHA актуален. Если PR закрыт или смержен, применяется его конечный статус.

Если вы вручную меняли файлы во время остановки пишущего агента, Harness не умеет
отличить эти правки от частичной работы агента. Их получит новая попытка, а
проверки и верификатор оценят итог. Не меняйте рабочую ветку параллельно запуску.

## Что continue не обходит

- NEEDS_CLARIFICATION: используйте `resume <run-id> --answer "..."` или файл ответов.
- Отрицательное решение, исчерпанный бюджет и эскалацию разработчику.
- Обычный технический BLOCKED без признака прерывания и без ожидающей доставки.
- COMPLETED/CANCELLED: такой запуск уже завершён.
- Отсутствие или изменение нужных артефактов, worktree и одобрений.

Уточнения через resume по-прежнему создают новый проход анализа/планирования
с ответами. continue продолжает текущий проход без новых ответов.
При resume под lock также проверяются исходный worktree, ветка и сохранённый HEAD.

Для прерванной доставки можно явно вызвать:

```sh
agent-harness retry-delivery <run-id>
```

Для ожидания PR и следующих проверок раз в час:

```sh
agent-harness watch <run-id> --loop
```

## Старые запуски и перенос

Точки продолжения создаются новой версией Harness. Старые RUNNING/BLOCKED без
checkpoint автоматически не мигрируются: вычислять этап по одному nextRole
небезопасно. История доступна через list/status/events, а существующие resume,
retry-delivery и watch работают в рамках собственных условий.

Для повторного использования результатов также нужен сохранённый artifactManifest.
Старые результаты без digest не получают фиктивную проверку задним числом:
continue/исправление PR остановится с объяснением. Resume с ответами создаёт
новый проход и новые результаты. Старые одобрения fingerprint, выданные для
удалений до исправления канонизации дерева, автоматически не переподписываются.

Рабочая папка запуска не является переносимым бэкапом: state.json содержит
машинные пути, а Git worktree связан с основным репозиторием. Для переноса
установите пакет и настройте новый ПК по [work-pc-setup.md](work-pc-setup.md).
Продолжение на том же ПК не перечитывает harness.config.json: используется
сохранённый config-снимок. Журнал events.jsonl остаётся диагностикой, состояние
не воспроизводится из него.
