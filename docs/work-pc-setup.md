# Перенос и настройка Agent Harness MVP на рабочем ПК

Документ описывает текущую реализацию проекта. Его задача — помочь развернуть
Harness, подключить рабочие LLM CLI/MCP/API и провести первый запуск.
Примеры путей нужно заменить своими. Команды рассчитаны на macOS/Linux;
для Windows используйте WSL2 и устанавливайте Node, Git, LLM CLI в том же окружении.

## 1. Что уже работает, а что предстоит подключить

Harness — программа на TypeScript, которая компилируется в JavaScript и работает
под Node.js 22+. Он управляет этапами, файлами, проверками, Git и доставкой.
LLM работает внутри отдельных процессов LLM CLI: анализирует, планирует,
пишет код, тесты и отчёты. MCP-инструменты вызывает LLM CLI по решению LLM.

| Часть | Состояние и настройка на рабочем ПК |
| --- | --- |
| Harness, роли, OpenSpec, проверки, Git worktree | Реализованы; нужны установка и конфиг продукта |
| LLM CLI | Установить и авторизовать по внутренней инструкции; проверить совместимость JSON-вывода |
| Codebase MCP и UI MCP | Есть учебные stdio-заглушки; заменить реальными серверами в настройках LLM CLI |
| Bitbucket | Протокол и цикл PR реализованы; сетевые операции реализовать в своём адаптере |
| трекер задач | Есть отправка отчётов/вопросов через адаптер; сетевую часть реализовать самостоятельно |
| Выбор/получение задачи из трекера задач | Пока не реализованы; вход — task.json и файл ТЗ |
| Получение ответов из комментариев | Пока не реализовано; ответы подаются через resume |
| Часовой цикл проверки PR | Реализован через watch --loop; отдельная служба/автозапуск не устанавливаются |
| Отдельные frontend/backend validator | Пока отсутствуют; есть общий verifier и обязательные проверки |
| Визуальное тестирование интерфейса | Не подключено; UI MCP используется как источник правил |
| Тест-кейсы задачи | Тестировщик пишет их в Test Cases файла test-report.md |
| Подготовка данных и тест-стори после аппрува PR | TODO; будущие скрипты описаны в [todo.md](todo.md) |

Установка папок `agents/` как отдельных расширений не требуется. Harness сам
загружает инструкции каждой роли и передаёт их LLM CLI.

## 2. Где что хранить

Рекомендуемая структура рабочего окружения:

```text
/work/tools/harness-agents-ai/       исходники Harness
/work/tools/company-adapters/       ваши скрипты Bitbucket и трекера задач
/work/projects/product-module/      продуктовый Git-репозиторий
  harness.config.json              поведение Harness для продукта
  harness.mcp.json                 образец определений MCP; сам не активируется
  harness-knowledge/               необязательная локальная база конвенций
  .harness/                        локальные задачи, логи и worktree
```

| Что меняется | Конкретное место |
| --- | --- |
| Команда LLM CLI, флаги модели, лимиты | `<продукт>/harness.config.json`: runner, runnerMode, timeoutMs |
| Установка зависимостей в worktree | Там же: setup |
| Typecheck/lint/test/build | Там же: checks |
| Исходная ветка и публикация | Там же: git |
| Запуск скриптов API | Там же: integrations.bitbucket / integrations.taskTracker |
| Официальная валидация OpenSpec | Там же: openspec.validator |
| Адреса API, проект Bitbucket, токены | Ваши адаптеры и окружение/хранилище credentials |
| Подключение MCP, транспорт, разрешения | Настройки установленного LLM CLI; не Config Harness |
| Локальные конвенции | knowledgeRoot и папки frontend/backend/testing |
| Инструкции ролей | `<Harness>/agents/<область>/<роль>.md` |
| Форматы отчётов | `<Harness>/agents/templates/` |
| Преобразование ответа LLM CLI | `<Harness>/src/agents/runner.ts`, если версия CLI несовместима |

Не добавляйте `projectRoot` в JSON: это поле отклоняется. Рабочий репозиторий
определяется командой `git rev-parse --show-toplevel` из текущей папки терминала.
Для monorepo это корень всего Git-репозитория.

## 3. Установка Harness

Проверьте инструменты:

```sh
node --version
npm --version
git --version
```

Node должен быть версии 22 или новее. Для первого подключения удобнее исходники:
вы сможете править адаптеры, инструкции и совместимость с корпоративным CLI.

```sh
cd /work/tools/harness-agents-ai
npm ci
npm run typecheck
npm test
npm run demo
npm link
agent-harness --help
agent-harness demo-review
```

`npm ci` запускает prepare и собирает dist. Демо используют детерминированные
заглушки, временные учебные репозитории и не обращаются к корпоративным сервисам.
Они проверяют механику Harness, но не авторизацию и не качество работы LLM.
Тест официального OpenSpec CLI без его настройки может быть пропущен.

Альтернатива для установки готового пакета:

```sh
npm install -g /path/to/agent-harness-mvp-0.1.0.tgz
agent-harness --help
```

Выберите один способ установки. При `npm link` после изменения TypeScript
выполните `npm run build`; команда использует dist, а не src. При установке
из tgz изменения исходников в другой папке не применяются: пакет нужно пересобрать
и переустановить. Markdown-инструкции читаются из установленной папки пакета.

В корпоративной сети npm должен использовать разрешённый registry и доверенные
сертификаты согласно вашей внутренней настройке. В репозитории нет отдельных
корпоративных npm/прокси/сертификатных настроек.

## 4. Подготовка продуктового репозитория

```sh
cd /work/projects/product-module
git status --short
git remote -v
git config user.name
git config user.email
git fetch origin
agent-harness init
```

Для Git-режима нужен хотя бы один существующий коммит и доступный baseRef.
Fetch выполняется вами: Harness не обновляет remote refs самостоятельно.
Права push понадобятся только при включении публикации.

`init` создаёт в корне продукта два файла: `harness.config.json` и
`harness.mcp.json`. Существующие файлы не перезаписывает. Если один файл уже есть,
команда может остановиться; проверьте оба файла перед повторением.

Добавьте `.harness/` в исключения Git продукта. Локальные конфиги с машинными
путями можно исключить через `.git/info/exclude`, если не хотите менять общий
`.gitignore`. Исключите и локальные секреты. Harness сам не настраивает эти
исключения за вас.

Незакоммиченные изменения основного checkout не переносятся в новый worktree.
Нужный исходный код и файлы сборки должны присутствовать в выбранном baseRef.
Исходное ТЗ считывается отдельно до создания worktree, поэтому оно может быть
локальным файлом вне коммита.

## 5. Конфиг для первого реального запуска без публикации

Пример полного `harness.config.json` для npm-проекта с четырьмя npm scripts.
Удалите отсутствующие команды и замените их реальными проверками вашего модуля.
Хотя бы одна обязательная проверка должна остаться.

```json
{
  "runner": {
    "command": "llm-cli",
    "args": []
  },
  "runnerMode": "cli",
  "timeoutMs": 600000,
  "maxOutputBytes": 8000000,
  "maxInputBytes": 4000000,
  "runnerInput": "stdin",
  "maxIterations": 3,
  "maxReworkRetries": 2,
  "git": {
    "enabled": true,
    "baseRef": "origin/main",
    "publish": false
  },
  "setup": [
    { "command": "npm", "args": ["ci"] }
  ],
  "checks": [
    { "name": "Typecheck", "command": "npm", "args": ["run", "typecheck"] },
    { "name": "Lint", "command": "npm", "args": ["run", "lint"] },
    { "name": "Tests", "command": "npm", "args": ["test"] },
    { "name": "Build", "command": "npm", "args": ["run", "build"] }
  ],
  "integrations": {}
}
```

Замените `origin/main` своей веткой, например `origin/dev`. Не оставляйте HEAD,
если адаптер создания PR не умеет преобразовать его в нужную целевую ветку.
HEAD подходит для локальной проверки, но не задаёт понятную целевую ветку PR.

Для backend замените setup/checks командами вашей сборки. Например, для проекта
с Gradle wrapper возможна проверка `{"name":"Backend tests","command":"./gradlew",
"args":["test"]}`. Она запускается из корня worktree; wrapper должен быть в Git
и иметь право исполнения. Для monorepo с подпроектами используйте параметры
вашего package manager/сборщика или отдельный wrapper-скрипт.

### Значение полей и правила путей

| Поле | Поведение |
| --- | --- |
| runner.command | Исполняемый файл в PATH или абсолютный путь |
| runner.args | Массив отдельных аргументов; Harness добавляет prompt и JSON-формат |
| runnerMode | cli — внешний массив сообщений CLI; protocol — прямой AgentResult |
| runnerInput | stdin по умолчанию; argv — совместимость с -p для запросов до 64000 байт, применяется только в cli |
| maxInputBytes | Общий бюджет сериализованного AgentRequest в UTF-8, по умолчанию 4000000 байт; превышение отклоняется до запуска CLI |
| timeoutMs | Таймаут одного процесса роли, setup или проверки; по умолчанию 600000 мс |
| maxOutputBytes | Общий предел stdout + stderr процесса; по умолчанию 8000000 байт |
| maxIterations | Предел итераций уточнений через resume; по умолчанию 3 |
| maxReworkRetries | Число доработок отдельно для плана и реализации; 2 означает первоначальную попытку + 2 доработки |
| git.enabled | true — отдельная ветка и worktree; false — работа прямо в текущем репозитории |
| git.baseRef | Локально доступный Git ref; автоматически fetch не выполняется |
| git.publish | true включает push и создание PR; требует git.enabled и Bitbucket-адаптер |
| setup | Одноразовые команды в новом worktree перед агентами |
| checks | Непустой массив обязательных проверок; ненулевой exit code не допускает успешную доставку |
| knowledgeRoot | Необязательный путь к конвенциям; без поля используется встроенная база |
| openspec.validator | Необязательная команда внешнего OpenSpec CLI |
| integrations | Команды ваших API-адаптеров; можно оставить пустым объектом |

`knowledgeRoot` считается относительно папки выбранного config-файла.
Другие строки путей не преобразуются автоматически в абсолютные пути.
`runner`, `setup`, `checks`, OpenSpec CLI выполняются из worktree, а адаптеры API —
из корня основного продуктового checkout. Для внешних скриптов используйте
абсолютные пути. Путь task.json в CLI считается от текущей папки терминала;
`specPath` внутри задачи — от корня продуктового репозитория.

Команды запускаются без shell. Не пишите `cd frontend && npm test` в command,
не ожидайте раскрытия `$VARIABLE`, `~`, `*.ts` или подстановки переменных в JSON.
Если нужна сложная подготовка, вынесите её в скрипт и передайте команду его запуска.
У объектов команд нет собственного поля cwd или env.

Без config Harness пытается найти typecheck/lint/test/build в корневом package.json.
При наличии packageManager pnpm/yarn использует его, иначе npm. `init` сохраняет
найденные проверки; после изменения package.json пересмотрите конфиг самостоятельно.
Массив checks из вашего конфига заменяет весь список по умолчанию.

Общий конфиг для нескольких репозиториев можно выбрать явно:

```sh
agent-harness run ./task.json --config /work/tools/company-settings/harness.config.json
```

Это не меняет целевой репозиторий: он определяется текущей директорией.

## 6. Настройка LLM CLI

`llm-cli` — условное имя внешнего CLI, а не пакет для установки. Задайте реальную
команду в `runner.command`. Режим `runnerMode=cli` ожидает описанные ниже флаги
и JSON-конверт; для другого интерфейса используйте wrapper с `runnerMode=protocol`.
Для ранее созданных конфигураций задайте `runnerMode=cli`, а адаптер трекера —
в `integrations.taskTracker`. Старые локальные состояния запусков автоматически
не мигрируются; новые задачи запускайте с обновлённой конфигурацией.

Установите CLI и выполните авторизацию по внутренней инструкции. В том же терминале,
из которого будете запускать Harness, проверьте:

```sh
llm-cli --help
```

Текущий адаптер делает следующий вызов из worktree:

```text
llm-cli <runner.args> --output-format json
# stdin: полный JSON AgentRequest
```

Новый процесс создаётся для каждого этапа. Сессия через continue/resume не
переиспользуется. Контекст, предыдущие отчёты и инструкции передаются в AgentRequest.
Не добавляйте `-p` и `--output-format` в runner.args повторно.

Стандартный транспорт — stdin: большой контекст не помещается в аргументы ОС.
Проверьте, что ваша версия CLI использует переданный stdin как headless-промпт.
Если нужен старый способ, задайте `"runnerInput": "argv"`: Harness добавит
`-p <JSON AgentRequest>`, но отклонит запрос больше 64000 байт до запуска.
Для больших запросов на CLI без stdin используйте совместимый wrapper в protocol
или адаптируйте runner к поддерживаемому файловому транспорту. Автоматического
повтора на argv после ошибки stdin нет.

maxInputBytes ограничивает весь запрос (ТЗ, инструкции, OpenSpec, прошлые отчёты
и результаты проверок), а не число токенов модели. Уменьшайте базу конвенций или
задавайте подходящий бюджет по возможностям модели. Превышение не обрезает ТЗ молча.

Ожидаемый stdout CLI:

```json
[
  {
    "type": "result",
    "subtype": "success",
    "is_error": false,
    "result": "{\"status\":\"COMPLETED\",\"summary\":\"...\",\"artifacts\":[],\"questions\":[],\"acceptance\":[]}"
  }
]
```

Это иллюстрация внешнего конверта, не готовый результат роли: в реальном запуске
обязательны файлы отчётов, а для некоторых ролей — дополнительные JSON-поля.
Парсер берёт последнее сообщение массива и разбирает result как JSON AgentResult.
`stream-json` с текущим runner несовместим. Логи не должны загрязнять JSON stdout.

Выбор модели, headless-разрешения, бюджеты CLI задавайте в runner.args или штатных
настройках LLM CLI по справке вашей версии. Например, флаг `--model` используйте
только если он поддерживается установленным CLI, с реальным идентификатором модели.

Обязательно проверьте доступность чтения/изменения файлов и MCP в headless-режиме.
Отсутствие интерактивного подтверждения не означает автоматическое разрешение
операции. Настройте permissions по внутренней политике; в Harness нет готовой
универсальной конфигурации разрешений LLM CLI. Не включайте режим CLI, который
отключает MCP или кастомные настройки, необходимые агентам.

Если формат вашей версии отличается, точка адаптации — `src/agents/runner.ts`:
`runAgent` формирует вызов, `parseAgentOutput` разбирает ответ. После правки
пересоберите Harness. `runnerMode=protocol` предназначен для своего wrapper:
он читает AgentRequest из stdin и печатает один прямой JSON AgentResult в stdout.
Сам LLM CLI нельзя просто переключить в protocol без такого wrapper.

## 7. Настройка Codebase MCP и UI MCP

### Кто подключает серверы

Harness не является MCP-клиентом и не читает harness.mcp.json при запуске ролей.
Подключать серверы нужно в **LLM CLI**, используя его штатный механизм MCP.
Точный путь файла настроек и способ регистрации зависят от корпоративной сборки CLI;
в текущем проекте они не зашиты. Возьмите их из внутренней инструкции или справки CLI.

Сгенерированный harness.mcp.json — образец определений stdio-серверов.
После переноса выполните init на рабочем ПК: старые абсолютные пути к Node и
установленному пакету с домашней машины работать не будут.

Схематичный пример для локальных рабочих серверов:

```json
{
  "mcpServers": {
    "codebase": {
      "command": "/absolute/path/to/node",
      "args": ["/work/tools/company-mcp/codebase/server.js"]
    },
    "ui-rules": {
      "command": "/absolute/path/to/node",
      "args": ["/work/tools/company-mcp/ui/server.js"]
    }
  }
}
```

Это форма определения stdio-серверов, а не гарантия пути/схемы конфигурации вашей
версии LLM CLI. Для HTTP/SSE/другого транспорта используйте поддерживаемую
конфигурацию LLM CLI; в Harness отдельного поля MCP endpoint нет.

### Какие данные и инструменты нужны

| Сервер | Минимальная потребность агентов | Учебные инструменты в этом репозитории |
| --- | --- | --- |
| Codebase | Поиск конвенций, реального API библиотек, примеров и зависимостей | search_knowledge(query), find_usage_example(query) |
| UI | Индекс UI-правил, конкретное правило и checklist | get_kb(), get_rule(id), get_ui_quality_checklist() |

Имена учебных инструментов не являются обязательным API корпоративного сервера.
Если рабочие инструменты называются иначе, поясните агентам их назначение в
локальных конвенциях и при необходимости в инструкциях frontend/analysis ролей.
Реальные параметры берите из схем инструментов рабочего сервера.

Frontend planner получает общие правила для дизайна. Frontend implementer сначала
читает утверждённый план, затем получает конкретные правила и API перед изменением
кода. В implementation.md обязателен раздел UI Rules: источники, требования,
места применения, противоречия. Существенный конфликт с дизайном приводит к
BLOCKED с запросом перепланирования; автоматического перехода из BLOCKED исполнителя
к планировщику сейчас нет. Общий verifier умеет вернуть REWORK_PLAN.

### Проверка подключения

1. Убедитесь, что LLM CLI показывает оба сервера и их реальные инструменты.
2. Через CLI запросите известную конвенцию и пример из рабочего проекта.
3. Проверьте корректность ответа и доступность сервера именно в headless-режиме.
4. Повторите проверку из отдельного Git worktree или его подпапки.
5. Проверьте, что результат не содержит mock=true и относится к нужному проекту.

Последний пункт существенен: агенты работают из `.harness/worktrees/<run-id>/`,
а локальная конфигурация LLM CLI, оставшаяся только в основном checkout и не
входящая в baseRef, может там отсутствовать. Используйте доступную из worktree
пользовательскую конфигурацию LLM CLI или другой поддерживаемый способ подключения.
Не рассчитывайте, что init автоматически скопирует и зарегистрирует MCP.

Заглушки находятся в `scripts/mcp-stub.ts`, после сборки — в
`dist/scripts/mcp-stub.js`. Они работают по stdio MCP, не принимают обычный текст
в качестве запросов. Все ответы имеют mock=true. Для корпоративной задачи,
которой нужны реальные правила, заглушки не подтверждают корректность решения.
Наличие UI Rules в отчёте проверяется кодом, факт вызова MCP инструментально
Harness пока не удостоверяет. Соответствие содержания оценивает verifier.

## 8. Локальные конвенции и skills

Встроенные конвенции находятся в `<Harness>/knowledge/`. Для своих правил добавьте
в конфиг продукта:

```json
"knowledgeRoot": "./harness-knowledge"
```

Структура обязательна, включая все три доменные папки:

```text
harness-knowledge/
  index.md
  frontend/conventions.md
  backend/conventions.md
  testing/conventions.md
```

Опишите архитектуру модуля, команды сборки/тестирования, где искать компоненты,
API, ограничения на изменения и назначение рабочих MCP. Не кладите туда токены.
В frontend-конвенциях удобно указать обязательную последовательность работы с
UI MCP и названия его реальных инструментов.

Для маленькой базы файлы .md выбранных доменов целиком загружаются в инструкции.
Аналитик и verifier получают все три домена; frontend/backend/testing — свой.
Внешний knowledgeRoot лучше хранить вне `.harness`: его путь должен быть доступен
всем процессам, включая worktree. Если не задавать поле, используется база пакета.

Сейчас явно подключается только `<Harness>/skills/project-conventions/SKILL.md`.
Новая папка skill сама по себе не включится. Для добавления других навыков нужно
изменить загрузчик `src/agents/instructions.ts` и явно задать привязку к ролям.
Произвольного реестра навыков в JSON-конфиге пока нет.

## 9. OpenSpec CLI

Harness сам создаёт change с proposal/specs/design/tasks и проверяет свой контракт.
Глобальная установка OpenSpec для этого не нужна. Если хотите также проверять
документы официальным CLI, установите разрешённую в компании версию и добавьте:

```json
"openspec": {
  "validator": { "command": "openspec", "args": [] }
}
```

Исполняемый файл должен быть в PATH процесса Harness или указан абсолютным путём.
Harness сам добавит `validate <change> --type change --strict --no-interactive`.
Не дублируйте эти аргументы в конфиге. Проверка идёт из worktree перед реализацией
и доставкой. Совместимость флагов проверьте у установленного OpenSpec CLI.

Полный контракт документов: [openspec.md](openspec.md).

## 10. Скрипты Bitbucket и трекера задач

### Общий протокол

Оба адаптера — обычные исполняемые программы, не MCP. Реализовать их можно на Node,
Python или другом доступном runtime. Harness не требует определённого HTTP SDK.

Каждый вызов:

- Запуск из корня основного продуктового checkout.
- Один JSON на stdin: version, operation, payload.
- Один JSON-объект на stdout, обязательно `ok: true` при успехе.
- Диагностика только в stderr; ошибка — ненулевой exit code или отсутствие ok:true.
- Таймаут адаптера — 60 секунд; timeoutMs из конфига его не меняет.
- Переменные окружения наследуются от процесса Harness.

Если скрипт написан на Node, при сборке JSON из stdin задайте
`process.stdin.setEncoding('utf8')` или используйте StringDecoder: граница
байтового chunk может проходить внутри кириллического символа.

Точный контракт запросов и ответов: [integrations.md](integrations.md).
Исходная заглушка: `scripts/mock-integration.ts`. Она не содержит готовых
корпоративных URL или авторизации — сетевые вызовы нужно реализовать.

Конфигурация команд после реализации:

```json
"integrations": {
  "bitbucket": {
    "command": "node",
    "args": ["/work/tools/company-adapters/bitbucket-adapter.mjs"]
  },
  "taskTracker": {
    "command": "node",
    "args": ["/work/tools/company-adapters/task-tracker-adapter.mjs"]
  }
}
```

Зависимости внешних адаптеров установите в их собственной папке.
Harness не выполняет npm install для них. Относительные пути внутри адаптера
привязывайте явно к файлу/его настройкам: process.cwd() будет продуктовым репозиторием.

### Bitbucket: что реализовать

В настройках своего адаптера задайте адрес и вариант Bitbucket (Cloud либо
Server/Data Center), проект/workspace, репозиторий, целевую ветку и авторизацию.
В Harness нет готовых полей для этих корпоративных значений: он знает только
command/args. Маппинг baseRef в целевую ветку выполняет адаптер.

| operation | Обязанность адаптера |
| --- | --- |
| pull-request.create | Найти существующий PR по ветке/ключу либо создать; вернуть ok:true и url |
| pull-request.get | Прочитать PR и все страницы обсуждений; вернуть нормализованные state, sourceCommit, threads |
| pull-request.reply | Ответить в существующий тред после проверки предусловий; вернуть ok:true |

Для get нормализуйте состояния в OPEN/MERGED/CLOSED, укажите реальный SHA исходной
ветки, стабильные id тредов/комментариев, автора, body и own. Сообщения в треде
возвращайте в хронологическом порядке. Не теряйте страницы API.
`own=true` исключает сообщение из обработки замечаний: при личном токене ручные
комментарии того же пользователя тоже могут исключаться. Продумайте различение
автоматизации; сервисная учётка упрощает его.

При create и reply реализуйте идемпотентность по payload.idempotencyKey, включая
ситуацию «сервер принял запрос, но ответ потерялся». Храните соответствие ключа
операции в устойчивом месте либо ищите уже созданный объект. Не храните его
только в памяти процесса: адаптер запускается заново на каждый вызов.

Перед reply перепроверьте открытый PR, expectedSourceCommit, незакрытый тред и
expectedThreadFingerprint. Алгоритм fingerprint — `src/review/identity.ts`:
SHA-256 JSON нормализованного треда с фиксированным порядком полей и только
человеческими комментариями. Если реализуете адаптер на другом языке, сохраните
совместимость сериализации. При изменении предусловий не публикуйте устаревший ответ.
Адаптер не должен выполнять merge или автоматически закрывать тред.

### трекер задач: что реализовать

Поддерживаемая операция одна: `task.report`. По taskId найдите задачу и опубликуйте
переданный отчёт/комментарий через API вашей установки. Автор определяется токеном
или сервисной учёткой адаптера. Реализуйте идемпотентность по idempotencyKey.

При NEEDS_CLARIFICATION публикуйте questions и контекст блокировки. При
returnToRole=developer учитывайте escalation и счётчики verification.retries:
кому назначить задачу, адаптер определяет по вашим настройкам. Не обязательно
менять статус задачи, если это не предусмотрено рабочим процессом: маппинг статусов
и назначений задаётся в вашем скрипте, не в LLM.

Аналитик сначала ищет ответы самостоятельно, включая Codebase MCP, затем задаёт
оставшиеся вопросы. Ответы из комментариев Harness пока не читает. Передайте их
через resume. Без адаптера вопросы и эскалация сохраняются локально.
Ошибка task.report записывается в integrationErrors и не обязательно меняет
основной статус задачи: всегда проверяйте и это поле.

### Credentials и окружение

Harness не читает .env автоматически и не раскрывает переменные в JSON.
Имена ниже — пример соглашения **для ваших скриптов**, а не встроенные поля Harness:

```text
COMPANY_BITBUCKET_URL
COMPANY_BITBUCKET_TOKEN
COMPANY_BITBUCKET_PROJECT
COMPANY_BITBUCKET_REPOSITORY
COMPANY_TASK_TRACKER_URL
COMPANY_TASK_TRACKER_TOKEN
```

Загружайте их разрешённым в компании способом перед запуском либо получайте
credentials внутри адаптера через штатное хранилище. Не вставляйте токены в
runner.args, integrations.args, task.json или knowledge: конфиг и запросы
сохраняются на диске в артефактах запуска.

Все дочерние процессы сейчас наследуют окружение Harness, включая LLM CLI.
Токены не добавляются в AgentRequest явно, но окружение не изолировано от LLM-процесса
с инструментами выполнения команд. Если credentials должны быть доступны только
интеграциям, получайте их внутри адаптера или используйте отдельные wrappers,
которые ограничивают окружение соответствующих процессов. Отдельного env-блока
на команду в текущем конфиге нет.

### Проверка адаптера до подключения к Harness

Пример безопасного чтения уже существующего тестового PR:

```sh
node /work/tools/company-adapters/bitbucket-adapter.mjs <<'JSON'
{"version":1,"operation":"pull-request.get","payload":{"url":"https://your-bitbucket/test-repo/pr/1","runId":"manual-check","branch":"codex/manual-check"}}
JSON
```

Замените URL и branch реальными значениями тестового репозитория. Проверьте,
что stdout — валидный JSON без баннеров, state нормализован, SHA настоящий,
все комментарии присутствуют. Create/reply/task.report проверяйте на тестовых
объектах; повтор одного idempotencyKey не должен создавать дубликат.

Не оставляйте mock-integration в конфиге для рабочего publish=true: учебный URL
не означает, что реальный PR существует.

## 11. Задача и первый запуск

В продуктовой папке создайте task.json, например:

```json
{
  "id": "FRONT-123",
  "title": "Обработка ошибки сохранения",
  "description": "Исправить поведение формы по приложенному ТЗ.",
  "specPath": "task-spec.md",
  "areas": ["frontend"],
  "acceptanceCriteria": [
    { "id": "AC-1", "description": "При ошибке сохранения введённые данные сохраняются." },
    { "id": "AC-2", "description": "Пользователь видит понятное сообщение и может повторить сохранение." }
  ]
}
```

В task-spec.md запишите полное ТЗ: исходное и ожидаемое поведение, ограничения,
состояния, API и известные критерии приёмки. Для совместной задачи areas содержит
`["frontend", "backend"]`. Для backend — `["backend"]`. Лишние роли соответствующей
области будут пропущены, но аналитик, тестировщик и verifier участвуют.

Первый запуск — с реальными MCP и git.publish=false:

```sh
cd /work/projects/product-module
agent-harness run ./task.json
```

Harness создаёт ветку codex/<task-id>-<uuid> от baseRef и worktree, выполняет setup,
затем аналитика → планировщиков → проверку плана → исполнителей → тестировщика →
проверку реализации. При одобрении создаётся **локальный коммит** в рабочей ветке.
`publish=false` не означает «не коммитить»; он отключает push и создание PR.

Сохраните выведенный run-id и путь run. Проверьте:

```sh
agent-harness status <run-id>
agent-harness events <run-id>
agent-harness list
```

Основные файлы:

```text
<продукт>/.harness/runs/<run-id>/
  state.json                  состояние, конфиг-снимок, результаты и ошибки интеграций
  report.md                   итоговая сводка
  specification.md            снимок исходного ТЗ
  events.jsonl                история этапов
  ...                         запросы, ответы и логи

<продукт>/.harness/worktrees/<run-id>/
  openspec/changes/.../       proposal, specs, общий design, tasks
  .harness/artifacts/.../     отчёты ролей и черновики
```

Для задачи с frontend проверьте implementation.md / UI Rules: реальные источники,
применённые правила и честные ограничения. Для всех задач проверьте design/tasks,
отчёт тестировщика, одобрение verifier, результаты обязательных команд и Git diff.
Форматы: [artifacts.md](artifacts.md), [verification.md](verification.md).

## 12. Уточнения, ошибки и изменения конфига

| Состояние | Что делать |
| --- | --- |
| NEEDS_CLARIFICATION | Прочитать questions, передать ответ через resume |
| RUNNING после аварии / BLOCKED с interrupted=true | agent-harness continue <run-id>: продолжение сохранённого прохода |
| Обычный BLOCKED до/во время ролей | Прочитать summary, отчёты и логи; continue не обходит ошибки или эскалацию |
| BLOCKED при доставке после одобрения | Если файлы и одобрения сохранены, использовать retry-delivery |
| WAITING_REVIEW | Включить watch или ожидать ручного ревью |
| COMPLETED | Локальная задача завершена либо PR смержен |
| CANCELLED | PR закрыт без merge; автоматизация остановлена |

```sh
agent-harness resume <run-id> --answer "При ошибке сохраняем поля и показываем сообщение."
agent-harness resume <run-id> ./answers.md
agent-harness retry-delivery <run-id>
```

Выберите один вариант resume. Это новый проход с ответами, а не продолжение
старой LLM CLI-сессии. Лимиты доработок при этом не обнуляются.
retry-delivery не обходит эскалацию, отсутствие одобрения или изменение файлов.

После остановки процесса найдите нужный запуск и продолжите его:

```sh
agent-harness list
agent-harness continue <run-id>
```

Завершённые роли не повторяются, прерванный этап получает новую попытку с
сохранённым контекстом в том же worktree. После аварии continue проверяет владельца
блокировки и оставшиеся дочерние процессы. Для старых запусков без checkpoint
автоматическое продолжение недоступно. Подробности: [continuation.md](continuation.md).

**Конфиг сохраняется в state.json при старте.** Команды continue/resume/watch/retry-delivery
используют этот снимок и не перечитывают harness.config.json. Параметры следующего
запуска меняются через исходный конфиг; для уже созданного запуска надёжнее
сохранять рабочие пути адаптеров и исправлять их реализацию/окружение. Поддерживаемой
CLI-команды изменения конфига существующего run сейчас нет. Не редактируйте
state.json как штатный способ перенастройки.

Коды CLI: 0 — COMPLETED/WAITING_REVIEW, 2 — NEEDS_CLARIFICATION, 3 — BLOCKED,
4 — CANCELLED, 1 — ошибка команды/конфига. `status` выводит сохранённый JSON.

## 13. Включение push, PR и обработки замечаний

После проверки локального сценария и реальных API-адаптеров:

1. Проверьте origin и права Git push.
2. Задайте baseRef, который адаптер однозначно переведёт в целевую ветку.
3. Подключите настоящий Bitbucket-адаптер со всеми тремя операциями.
4. По необходимости подключите трекер задач.
5. Поставьте git.publish=true и запустите **новую** задачу.

```sh
agent-harness run ./task.json --watch
```

После одобрения Harness коммитит, пушит в origin, создаёт PR и переходит в
WAITING_REVIEW. Флаг --watch продолжает наблюдение: первый опрос сразу, следующие
примерно через час после завершения предыдущей обработки. Новое замечание разбирает
review-triager, исправления проходят проверки и verifier, пушатся в ту же ветку,
после чего публикуется ответ. Две коррекции на тред, далее эскалация; внутренние
лимиты доработок тоже действуют и могут остановить процесс раньше.

Для уже созданного PR-запуска:

```sh
agent-harness watch <run-id>
agent-harness watch <run-id> --loop
```

Первая команда делает один проход, вторая работает циклом. Не запускайте их
одновременно для одного run. Ноутбук должен оставаться включённым, процесс —
работать; после закрытия терминала самостоятельной фоновой службы не появляется.
Для своего scheduler используйте одноразовый watch. После merge — COMPLETED,
после закрытия без merge — CANCELLED. Harness не выполняет merge сам.

При отсутствии новых тредов LLM не вызывается. В одном опросе обрабатывается до
20 новых/изменённых человеческих тредов. Не меняйте ветку автоматизации вручную
во время цикла: неожиданный SHA останавливает автоматическую доставку.
Подробности: [pr-review.md](pr-review.md).

## 14. Частые проблемы и точка исправления

| Симптом | Что проверить |
| --- | --- |
| agent-harness не найден | npm link/global install, PATH текущего терминала |
| LLM CLI не найден | runner.command и PATH именно процесса Harness |
| Expected LLM CLI JSON message array | runnerMode, формат stdout, совместимость runner.ts |
| LLM CLI did not return a successful result | Итоговое сообщение CLI, авторизацию, ошибки и лимиты |
| exit 53 / exit 55 | Лимит turns / бюджета CLI; проверить флаги вашей версии |
| Process timed out | timeoutMs для ролей/checks; у API-адаптера отдельные 60 секунд |
| MCP есть в IDE, но нет у агента | Настройки LLM CLI, headless permissions, доступность из worktree |
| В ответах mock=true | Подключены учебные MCP, корпоративные правила ещё не доступны |
| Не найден модуль/зависимости продукта | setup, registry, сертификаты; node_modules основного checkout не копируется |
| Cannot fingerprint / отсутствует baseRef | Состояние Git, fetch, доступность ref и файлов |
| Ошибка обязательного отчёта/раздела | agents/templates и результат роли; нельзя заменять отчёт произвольным файлом |
| Adapter did not confirm success | stdout должен быть одним JSON с ok:true; логирование перенести в stderr |
| PR не создан, но ветка появилась | Push предшествует API create; исправить адаптер и проверить условия retry-delivery |
| Дублируются PR/комментарии | Идемпотентность корпоративного адаптера |
| трекер задач молчит при успешном run | integrations.taskTracker, credentials, integrationErrors в state.json |
| Правка конфига не действует на watch | Run использует сохранённый config-снимок |
| Files changed after verifier approval | Файлы/хуки изменили проверенный результат; нужна новая верификация |
| Остался run.lock после аварии | continue восстанавливает lock мёртвого локального PID; живые/неизвестные процессы требуют проверки, см. continuation.md |

Не запускайте npm pack/npm run build одновременно с тестами или работающим
Harness из той же установки: сборка очищает dist, а npm pack вызывает prepare.
Проверки, сборку и упаковку выполняйте последовательно.

## 15. Когда окружение можно считать подключённым

- Демо и локальные проверки Harness проходят.
- LLM CLI запускается в headless, возвращает ожидаемый JSON и создаёт отчёты.
- Реальные Codebase/UI MCP доступны из worktree; известные запросы дают рабочие данные.
- Setup подготавливает чистый worktree, checks проверяют нужные части продукта.
- Локальная задача проходит до одобренного коммита без публикации.
- Bitbucket create/get/reply проверены, повтор запросов не создаёт дубликатов.
- трекер задач получает отчёты и вопросы от ожидаемой учётной записи, если интеграция включена.
- Тестовая задача создаёт настоящий PR, замечание вызывает проверенное исправление,
  а merge завершает run.

После этого для повседневной работы остаются подготовка входной задачи и запуск
из нужного репозитория. Автоматический выбор задачи из трекера задач — отдельный
ещё не реализованный шаг, а не скрытая настройка этого MVP.
