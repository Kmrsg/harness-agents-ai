# OpenSpec в Harness

Основа — стандартная [схема spec-driven](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml).
Разделение между ролями и owner-теги задач — соглашение этого Harness.

## Роли и переходы

| Этап | Результат |
|---|---|
| Аналитик | `proposal.md` и delta specs для объявленных capabilities |
| Backend-планировщик | Общие `design.md`, `tasks.md`: backend-контракт и задачи backend/testing |
| Frontend-планировщик | Дополняет те же файлы frontend-разделом и задачами frontend/testing |
| Верификатор плана | Сопоставляет design/tasks с ТЗ и specs; одобряет или возвращает план |
| Backend-исполнитель | Код, отчёт, выполненные backend-задачи |
| Frontend-исполнитель | Код, отчёт, выполненные frontend-задачи |
| Тестировщик | Проверка сценариев specs и критериев, отчёт, выполненные testing-задачи |
| Верификатор реализации | Сопоставляет код с одобренным планом/specs и проверками; решает, куда вернуть работу |

Для одной области лишние роли пропускаются. В MVP design обязателен даже для
небольшой задачи: он задаёт явную точку передачи работы планировщика исполнителю.
После всех планировщиков Harness проверяет полноту design/tasks, затем верификатор
проверяет содержательное соответствие требованиям. Только после одобрения запускается код.

Каждая роль также создаёт собственный отчёт по [контракту артефактов](artifacts.md).
Его нельзя заменить только черновиком design/tasks. Общие разделы design —
Context, Decisions, Risks / Trade-offs — обязательны наряду с Backend/Frontend;
проверка выполняется до публикации черновиков.

## Владение документами

В `AgentRequest.openspec` передаются:

- `name`, `directory`: имя и путь общей папки change относительно workdir;
- `files`: актуальные документы change с содержимым;
- `baselineSpecs`: основные спецификации из `openspec/specs`;
- `draftDirectory`: место для полных обновлённых копий документов внутри артефактов роли.

Агент включает черновики в `result.artifacts`. Harness проверяет набор документов,
права роли, сохранение чужих задач и публикует проверенную версию в change.
Прямое изменение общих документов или основных specs обнаруживается после этапа
и блокирует продолжение. Это проверка целостности, а не OS sandbox: уже сделанная
несанкционированная запись автоматически не откатывается и требует просмотра.

Снимок каждой опубликованной версии лежит в run-каталоге
`<iteration>-<role>.openspec/`. Исходное ТЗ хранится отдельным неизменяемым снимком
`specification.md`. Его путь в задаче не становится путём выходного change.

## Формат задач

```markdown
# Tasks

## 1. Backend
- [ ] 1.1 [backend] Реализовать валидацию AC-1; проверить API-тестом.

## 2. Frontend
- [ ] 2.1 [frontend] Показать ошибку AC-1; проверить тестом формы.

## 3. Testing
- [ ] 3.1 [testing] Проверить AC-1: пустой ввод отклоняется UI и API.
```

Нумерация `X.Y` уникальна для всего файла. Owner — `backend`, `frontend` или
`testing`. Планировщики добавляют только невыполненные задачи своей области и
тестирования. Другие задачи и уже описанный контракт в `## Backend`/`## Frontend`
сохраняются. При `rework.phase=plan` планировщик может пересмотреть свои задачи и
testing, сохраняя задачи и раздел дизайна другой области. Исполнители и тестировщик могут менять только флажки своих задач;
текст, порядок, определения и чужие флажки сохраняются. При `COMPLETED` роли её
задачи должны быть выполнены. Финальный COMPLETED требует закрытия всех задач,
подтверждения критериев тестировщиком, успешных обязательных проверок и одобрения верификатора.

## Уточнения

При NEEDS_CLARIFICATION документы этого этапа не публикуются. Harness сохраняет
вопросы локально, передаёт их настроенному скрипту трекера задач для публикации
комментария и останавливает следующие роли. Аналитик задаёт вопросы только после
попытки найти ответы в ТЗ и проекте, включая Codebase MCP. `resume` передаёт ответы аналитику вместе
с исходным ТЗ и предыдущими документами. После успешного анализа обновляются
proposal/specs, старые design/tasks исключаются из активного change, затем
планировщики создают их заново. Старые версии сохраняются в снимках.

Поэтому выполненные флажки предыдущей итерации не переходят автоматически в новую:
реализация повторно сверяется с уточнёнными требованиями. Код остаётся в worktree.
Та же инвалидация флажков происходит при доработке после review. Бюджеты доработок
сохраняются между итерациями уточнений. Правила возврата: [verification.md](verification.md).

## Проверка и жизненный цикл

Без установленного CLI Harness проверяет собственный контракт: наличие артефактов,
соответствие capabilities и spec-путей, базовую структуру требований/сценариев,
связь с AC-id, владение задачами и полноту checklist. Это не полная реализация
официального валидатора и не проверка смысловой полноты требований.

При настройке `openspec.validator` код запускает
`validate <change> --type change --strict --no-interactive` после планирования
и после финальных проверок, перед соответствующим review. Ошибка передаётся
верификатору как доказательство необходимости доработки и блокирует одобрение.
Логи всех проверок сохраняются в `N-<phase>-rework-M-check-K.log`, пути есть в state.json.

Для повторяемой интеграционной проверки с установленным CLI:

```sh
OPENSPEC_TEST_CLI=openspec OPENSPEC_TELEMETRY=0 npm test
```

Без `OPENSPEC_TEST_CLI` внешний интеграционный тест пропускается; остальные тесты
и демо не требуют OpenSpec CLI. Зависимость CLI не добавлена в package.json:
рабочий ПК может использовать принятую в команде версию.

В первой версии поддерживаются продуктовые изменения с delta specs. `skip_specs`,
пользовательские схемы, standalone stores и автоматический archive не поддержаны.
Основные specs обновляются отдельным процессом archive после принятого в команде
ревью; COMPLETED Harness не означает, что change уже слит или архивирован.
