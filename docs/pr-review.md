# Цикл ревью PR

При `git.publish=true` успешная публикация переводит запуск в `WAITING_REVIEW`.
`COMPLETED` означает merge PR; закрытие без merge даёт `CANCELLED`. При локальном
режиме без публикации прежний `COMPLETED` означает проверенную локальную реализацию.
Статусы отдельных LLM-ролей по-прежнему COMPLETED/NEEDS_CLARIFICATION/BLOCKED.

## Запуск

```sh
agent-harness watch <run-id>
agent-harness watch <run-id> --loop
agent-harness run task.json --watch
```

`run ... --watch` после успешной публикации сразу запускает тот же часовой цикл.
При NEEDS_CLARIFICATION/BLOCKED запуск возвращает управление вместо ожидания.

Первая команда делает один проход и подходит для вашего системного планировщика
раз в час. Вторая сразу делает проход, затем повторяет через час после завершения
предыдущего, пока статус WAITING_REVIEW. Компьютер и процесс должны работать;
фоновой службы/автоматической регистрации расписания нет. Ctrl+C завершает ожидание.
После перезапуска вызывайте ту же команду с тем же run-id: история хранится в state.json.
Неизменившийся PR не вызывает LLM. За проход обрабатываются до 20 новых/изменённых
незакрытых тредов с человеческими комментариями. Остальные остаются на следующий проход.
Треды обрабатываются последовательно под общим run.lock.

## Маршрутизация

`review-triager` читает текущие OpenSpec документы, код, тред и результаты проверок.
Он не изменяет продуктовые файлы. Его структурированное решение:

| action | Действие Harness |
| --- | --- |
| FIX_IMPLEMENTATION | Участвующие исполнители → тестировщик → проверки → верификатор реализации |
| FIX_PLAN | Участвующие планировщики → проверка плана → исполнители → тестировщик → проверка реализации |
| REPLY | Ответ с обоснованием, без изменения кода |
| CLARIFY | Вопрос ревьюеру в том же треде, ожидание нового человеческого комментария |

Аналитик не переписывает исходную спецификацию автоматически по комментарию PR.
Новые продуктовые требования требуют явного согласования: triager спрашивает
ревьюера, а изменение исходного ТЗ остаётся за человеком. Треды автоматически не
закрываются. Ответы публикуются скриптом от настроенной учётной записи.
При FIX_* текущий план сохраняется, его задачи переоткрываются. При FIX_PLAN
пересматриваются design/tasks. Тред передаётся всем ролям, включая финального
верификатора, и остаётся в контексте повторных проверок. Нужны доказательства
устранения замечания и прохождение проверок. Затем коммит/push в ту же ветку,
без создания второго PR, и ответ со ссылкой на коммит.

Две коррекции на один thread-id допускаются суммарно, даже если текст комментария
изменён. Отдельные существующие бюджеты двух доработок плана/реализации сохраняются
и также могут остановить процесс раньше. Часовые проходы счётчики не сбрасывают.
Исчерпание бюджета/неудачная коррекция → BLOCKED, nextRole=developer, отчёт.
Для продолжения после эскалации нужна проверка разработчика; watcher сам BLOCKED
не снимает. Merge/закрытие всё ещё можно обнаружить отдельным вызовом watch.

## Состояние и сбои

- Хеш треда учитывает человеческие комментарии, включая редактирование. Ответы
  собственной учётки исключаются: важно правильно заполнить `own` в адаптере.
- Точный текст ответа и idempotencyKey сохраняются до вызова API. При потере ответа
  повторяется тот же запрос, без нового вызова модели, если тред и HEAD актуальны.
  Если тред изменён, закрыт или удалён, ответ получает stage=superseded и не
  отправляется. Изменённый человеческий тред разбирается заново на следующем
  проходе; прежние попытки исправления остаются в общем счётчике.
  Адаптер обязан исключать дубли и проверять expectedThreadFingerprint.
- Перед изменениями проверяются HEAD, чистота worktree, head удалённой ветки и PR.
  Изменения другого разработчика приводят к эскалации, без автоматического reset/rebase.
- Перед push ещё раз проверяется PR; ancestry-проверка и Git lease защищают чужие
  коммиты от перезаписи. Неатомарную гонку merge между чтением API и push полностью
  устранит только серверная политика Bitbucket; настройте запрет push в завершённые PR,
  если она доступна в вашей установке.
- Ошибка чтения API сохраняется в integrationErrors; следующая проверка повторит запрос.
  Это действует и для повторных GET перед triage/исправлением. Ошибочный контракт
  успешного снимка PR и обнаруженная смена SHA остаются отдельными причинами остановки.
  Ошибка отправки ответа оставляет сохранённый ответ для повторной доставки.
- При временной ошибке push/доставки одобренного исправления сохраняется
  deliveryPending. `retry-delivery` повторяет проверки и доставку без новых ролей,
  затем отправляет сохранённое обоснование в тред; повтор ответа защищён ключом.
- После аварии watcher сам не повторяет незавершённое исправление: используйте
  `agent-harness continue <run-id>` для новых запусков с checkpoint. Сохраняются
  контекст треда и бюджет коррекций; перед продолжением проверяются SHA и fingerprint
  обсуждения. При изменении треда или внешней смене ветки требуется разработчик.
  Неизвестная старая блокировка удаляется вручную только после проверки,
  что предыдущий процесс и его дочерние процессы действительно остановлены.
- MERGED завершает задачу, CLOSED прекращает работу. Сам Harness merge не делает.

## Локальная демонстрация

```sh
agent-harness demo-review
```

Создаёт временный Git-репозиторий и локальный bare remote. Mock-агенты создают PR,
исправляют mock-замечание, проходят проверку, отправляют ответ в файл, пропускают
повторно обработанный тред и обнаруживают mock-merge. Реального Bitbucket и LLM нет.
В конце выводятся пути проекта, отчёта и файла ответов; они остаются для изучения.

Для ручных экспериментов скопируйте examples/pr-review.mock.json за пределы
продуктовой ветки и задайте абсолютный путь в HARNESS_BITBUCKET_FIXTURE. Подключите
скомпилированный scripts/mock-integration.js как Bitbucket adapter. В исходниках
он расположен в scripts/mock-integration.ts, в установленном пакете — dist/scripts/.
`sourceCommit: "REMOTE"` — специальное значение только заглушки: берёт реальный
head ветки из локального origin. Обычный API-адаптер должен возвращать SHA.

Меняйте comments, resolved, state (OPEN/MERGED/CLOSED) и запускайте watch.
Mock-triager распознаёт маркеры [fix], [fix-plan], [question]; остальные комментарии
получают mock-ответ REPLY. Ответы записываются в `<fixture>.replies.jsonl`.
Для настоящего подключения замените операции get/reply в скрипте на API вашей
версии Bitbucket; точный контракт описан в integrations.md.
